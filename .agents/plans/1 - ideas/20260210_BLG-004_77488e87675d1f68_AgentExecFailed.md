## Title

Classify Claude terminal failures (quota vs execution) instead of generic code-1/AgentExecFailed

## Problem

Claude adapter failures are being collapsed into generic `AgentExecFailed` / `claude exited with code 1`, even when provider-specific signals (for example quota-limit reset messages) exist.

## User impact

Users and triage tooling cannot distinguish quota exhaustion from auth/runtime/transport faults, causing mis-triage, delayed recovery, and repeated failed runs.

## Proposed fix

Implement deterministic Claude error normalization that maps raw exit/message/artifact signals to typed reason codes (including explicit quota-limit with reset guidance) and propagate those fields through user-visible errors and report validation artifacts instead of generic code-1 outcomes.

## Investigation steps

- Trace where Claude stderr/last-message/provider payloads are reduced to `AgentExecFailed` or plain exit-code errors.
- Define a typed failure taxonomy (quota_limit, auth, transport, timeout, harness_exception, unknown).
- Add parsing/mapping rules for known Claude limit strings and provider terminal conditions.
- Populate normalized reason metadata in adapter outputs and report-validation inputs.
- Add integration/regression tests covering quota-limit and non-quota code-1 paths.

## Success criteria

- Quota-limit cases surface a specific quota reason code plus reset-time guidance.
- Generic `AgentExecFailed`/`code 1` is not the only final failure detail when richer signals exist.
- Validation artifacts include machine-readable domain/reason fields for grouping.
- Triage can reliably distinguish quota failures from runtime/transport/auth failures.
