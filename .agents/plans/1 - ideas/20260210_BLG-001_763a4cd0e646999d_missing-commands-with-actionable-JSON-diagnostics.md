## Title

Fail-fast capability preflight for blocked/missing commands with actionable JSON diagnostics

## Problem

Required workflow commands are blocked or unavailable, but this is only discovered after attempting normal workflow steps, yielding generic policy rejections instead of clear preflight diagnostics.

## User impact

Users fail before first successful run, misdiagnose repository health, and lack a clear triage/remediation path when command execution is blocked by policy.

## Proposed fix

Add a runner startup preflight that checks required command executability/permission before any workflow dispatch, then fails once with structured machine-readable diagnostics (per-command status such as available/missing/blocked_by_policy, failure domain, and remediation hints), and document the blocked-policy decision path.

## Investigation steps

- Reproduce policy-blocked and missing-command scenarios and capture current error payloads.
- Define a required-command matrix per workflow entrypoint.
- Specify a stable preflight JSON contract (error code, command, status, failure domain, remediation).
- Implement the probe in runner entrypoint so it executes before install/test/scaffold commands.
- Wire orchestration to stop downstream workflow steps on failed preflight and persist diagnostics artifact.
- Add docs/playbook branch for blocked-by-policy vs missing-tool vs repo/runtime failure.
- Reproduce with the same runner profile using `pdm run pytest` and `python -m pytest -q` and capture policy rejection messages.
- Audit effective allow/deny rules for `python`, `pdm`, and `pytest`, and compare against a known-good profile.
- Apply minimal allowlist/profile fix and rerun baseline commands to confirm they start execution.

## Success criteria

- First failure in blocked/missing environments is the preflight result, not a mid-workflow command rejection.
- Diagnostics artifact is machine-readable and includes command name, status, and failure domain.
- Output includes at least one actionable remediation path for blocked/missing commands.
- Downstream workflow steps are skipped when preflight fails.
- Generic "blocked by policy" messages are not emitted without contextual diagnostics.
- Baseline commands (`pdm install`, `pdm run pytest`, `python -m pytest -q`) start execution instead of immediate policy rejection.
- At least one end-to-end harness workflow proceeds past command launch to real dependency/runtime outcomes.
- If a command is blocked, runner returns a stable machine-readable `policy_block` reason before task execution.
